# План производства

## Подтверждённый brief

- Платформа: Steam.
- Кооперативная игра про переноску мебели из домов с денежной квотой.
- Изометрическая камера, простая мультяшная графика.
- Изображения в `outputs/` — предварительные визуальные ориентиры.
- Команда: координатор → project_manager → gamedev_developer → qa_reviewer → project_manager. Координатор управляет передачами и общением с пользователем.

## Открытые решения

- Движок, язык, версия инструментов и сетевой стек не выбраны. Решение ENG-001 необходимо до реализации.
- Число игроков, модель коопа, целевые ОС, управление, длительность смены и точные правила квоты не утверждены.
- Хоррор, проклятая мебель, повреждения груза, инструменты, прогрессия и нарастающая опасность — обсуждавшиеся предложения, а не обязательный scope.

## Порядок работы

Статусы: `backlog → ready → in_progress → review → done`. Дефекты возвращают задачу в `in_progress`; `blocked` требует конкретной внешней зависимости. Закрывает PM после независимого QA и доказательств по обязательным критериям. Непроведённые проверки остаются явно непроведёнными.

В работе у разработчика одна назначенная задача. Перед QA он передаёт стабильное состояние, список файлов, команды и результаты проверок. На время QA эти файлы не меняются. При отсутствии Git координатор фиксирует проверяемые файлы и состояние явно. QA не исправляет реализацию самостоятельно.

## TEAM-001 — Настройка оркестрации

- Статус: `review` — ожидает технической валидации и независимого QA; статус не означает завершение проверки.
- Владелец: координатор; планирование — project_manager; валидация — gamedev_developer; ревью — qa_reviewer.
- Цель: сохранить три роли и воспроизводимый процесс передачи задач в проекте.
- Зависимости: доступные инструменты субагентов текущей сессии; выбранный движок не требуется.
- Scope: `AGENTS.md`, `.codex/config.toml`, три файла `.codex/agents/*.toml`, этот backlog; отчёты в `work/production/`.
- Вне scope: игровой код, установка движка, выбор сетевого стека, разработка MVP.

Критерии приёмки:

1. Есть три роли с уникальными именами `project_manager`, `gamedev_developer`, `qa_reviewer`, описаниями и инструкциями.
2. Все четыре TOML-файла разбираются настоящим TOML-парсером; имена и непустые обязательные поля проверены.
3. Зафиксированы последовательные передачи PM → разработчик → QA → PM, цикл исправлений, владение файлами и запрет самостоятельной приёмки разработчиком.
4. Ограничение конфигурации — три одновременно открытых субагента; вложенные субагенты запрещены инструкцией.
5. Реально запущены три роли и проведена передача PM → разработчик → QA → PM. В этом сеансе инструкции передаются явно; автоматическая загрузка клиентом не является критерием, перечитывание `.codex/` новым сеансом не проверено.
6. Независимый QA сопоставил критерии с доказательствами и выдал PASS либо конкретные замечания/блокеры.

Проверки и evidence:

- PM прочитал `AGENTS.md` и `.codex/agents/project_manager.toml`; создан этот backlog.
- Разбор TOML: ожидает разработчика.
- Исполнение ролей: по сообщению координатора три роли успешно запущены; разработчик и QA подтвердили чтение инструкций. PM подготовил передачу; техническая валидация, независимое QA и возврат PM ещё ожидаются.
- Независимое QA: не проведено. Задача не закрыта.

## Передача разработчику: TEAM-001 / техническая валидация

- Цель: проверить конфигурацию команды без начала разработки игры.
- Входы: `AGENTS.md`, `.codex/config.toml`, `.codex/agents/project_manager.toml`, `.codex/agents/gamedev_developer.toml`, `.codex/agents/qa_reviewer.toml`, этот backlog.
- Разрешённые изменения: только назначенный координатором отчёт `work/production/team-001-dev-validation.md`. Если найдена ошибка конфигурации — сообщить координатору точный дефект; не менять файлы PM и проверяемые роли без нового поручения.
- Проверки: настоящий TOML-разбор; уникальность имён и наличие непустых `name`, `description`, `developer_instructions`; значение лимита; согласованность ролей с процессом; отсутствие преждевременного выбора движка.
- Критерий результата: отчёт с командами, фактическими результатами, перечнем проверенных файлов и ограничениями. Не утверждать автоматическую загрузку ролей клиентом только на основании синтаксиса TOML.
- Следующий шаг: координатор передаёт стабильные файлы и отчёт независимому `qa_reviewer`.
