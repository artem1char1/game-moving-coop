# ТЗ первой итерации — SPEC-001

**Статус: согласовано пользователем 31.10.2026. Первая итерация IT1-01…IT1-06 разрешена к реализации.**
Основание: ответ пользователя «хорошо, приступайте». Исходные числа, кнопки, правила и критерии сохранены; их прежние пометки «предложено» обозначают происхождение согласованного прототипного дизайна, а не необходимость повторного разрешения.
Основа: выбранный Unity 6000.6.7f1 / URP / C#, кооперативные переезды, изометрия, простая мультяшная подача и денежная квота.

**Дополнение SOLO-001 от 01.11.2026:** по запросу пользователя разрешён старт хостом в одиночку. Это отменяет прежнее требование второго игрока для Start; если подключены двое, готовность требуется от обоих. Второй игрок присоединяется только в подготовке. Квота320,300сек и диван на двоих сохраняются; одному достаточно восьми коробок. Кооп остаётся доступен.

## 1. Результат итерации

Два игрока входят в небольшой дом, выносят груз в зону фургона и пытаются собрать квоту за одну смену.
Нужно проверить, приятно ли совместно тащить диван, координироваться в дверях и выбирать между несколькими лёгкими грузами и одним тяжёлым.
Поставка после будущей реализации: запускаемая Windows PC-сборка, одна тестовая локация и инструкция подключения двух процессов.
Кооп: host + один клиент через localhost или прямое подключение по LAN. Сетевой стек пока не выбран.
Steam — целевая площадка продукта; Steam invites, интернет-матчмейкинг, NAT traversal и Steamworks в эту итерацию не входят.

## 2. Локация и тестовые параметры

- Greybox: три комнаты, общий коридор, выход наружу и отмеченная прямоугольная зона сдачи у неподвижного фургона.
- Простые цветные формы без финального арта, анимаций и декоративного наполнения; игроки различаются цветом.
- В каждой комнате есть свободный подход к грузу; минимум один поворот требует разворота дивана.
- Предложенный диван: 2,2 × 0,9 м; чистая ширина дверей не меньше 1,6 м. Маршрут проверяется с двумя носильщиками, а не только моделью дивана.
- Груз: девять лёгких коробок по 40 единиц и один диван за 200. Стоимости фиксированы, денег между сменами нет.
- Квота: 320, время: 300 секунд. Достижение квоты само по себе не заканчивает смену.
- Два варианта цели: восемь коробок = 320 либо диван + три коробки = 320; всего доступно 560; лёгкого груза доступно 360, одна коробка остаётся запасной.
- Лёгкий путь допускает параллельные рейсы, тяжёлый требует координации обоих игроков. Баланс времени — гипотеза для playtest, не обещание равной сложности.
- Предложенные скорости: без груза 4 м/с, коробка 3 м/с, диван 2 м/с; ускорение/инерция не обязательны.

## 3. Управление и камера

| Действие | Предложенная кнопка / правило |
| --- | --- |
| Движение | WASD по экранным направлениям, проекция на горизонтальную плоскость; диагональ нормализована |
| Взять / отпустить | E; если игрок уже держит груз, E только отпускает его |
| Вращать груз | Удержание Q / R: против / по часовой стрелке при взгляде сверху, 90°/с |
| Эвакуация | F у фургона, только хост и только при выполнении условий §6 |
| Начало / повтор смены | Кнопка хоста в интерфейсе подготовки / результата |

Камера ортографическая изометрическая, следует за своим игроком, без пользовательского вращения и зума в этой итерации.
W перемещает к верхней стороне экрана, D — к правой; направление не зависит от ориентации персонажа.
Стены, перекрывающие своего игрока или удерживаемый груз, локально скрываются/становятся прозрачными и восстанавливаются после ухода; коллизии остаются.
Персонажи и груз сталкиваются со стенами и полом; игроки друг друга не блокируют. Нет прыжка, спринта, броска и толкания свободного груза телом.

## 4. Захват и переноска

1. Каждый игрок держит не больше одного предмета. Для взаимодействия выбрать ближайшую свободную ручку в пределах 1,2 м, без стены между игроком и ручкой. Вход к ручке выполняется по проверенному коллизиями пути сближения либо захват отклоняется; мгновенный перенос и привязка сквозь стену запрещены.
2. При равной дистанции выбор стабилен по CargoId/HandleId; подсветка и подсказка показывают цель до нажатия E.
3. Коробка имеет одну ручку и перемещается одним игроком. Диван — две разные ручки на противоположных концах, по одной на игрока.
4. Первый носильщик дивана получает ручку, но не двигает и не вращает диван; сам остаётся у ручки и может отпустить её. UI: «Нужен второй игрок».
5. При двух носильщиках движение дивана задаёт среднее нормализованных WASD-векторов игроков: одинаковый ввод даёт полную скорость, встречный — остановку, ввод одного — половину скорости.
6. Для дивана Q/R обрабатываются только от первого захватившего ручку игрока; он отмечен в UI как управляющий вращением. Для коробки управляет её носильщик. Q+R одновременно дают ноль вращения.
7. Носильщики следуют за ручками; движение и вращение ограничиваются общим допустимым положением груза и игроков. Столкновение блокирует запрещённую часть движения, без прохода сквозь стену и без телепортации.
8. Если один отпускает диван, освобождаются обе ручки: он остаётся в последней подтверждённой допустимой позе, оба игрока свободны. При повторном захвате требуется снова два игрока.
9. Свободный или отпущенный груз не летит и не получает импульс; он сохраняет положение на полу. При невозможности применить движение используется последняя безопасная поза, без тихого рассогласования состояния.
10. Два запроса одной ручки разрешает порядок валидных команд хоста: один выигрывает, второй получает «Занято». Разные ручки дивана могут быть заняты обоими.
11. При отключении клиента освобождается его коробка либо обе ручки дивана. Поздние команды старого соединения отклоняются; хост видит сообщение, завершает Active эвакуацией по §6 и может перезапустить только с экрана результата.
12. При выходе хоста сессия заканчивается с понятным сообщением клиенту. Reconnect, миграция хоста и восстановление после падения исключены.

При потере фокуса локальный ввод движения/поворота обнуляется и отправляется release/focus-сигнал для отпускания груза. На authority отсутствие свежих сообщений до timeout также обнуляет непрерывный ввод и освобождает участие игрока по правилу отпускания; значение timeout и доставка release/focus определяются в tech gate, без доверия к обязательному приходу последнего сообщения.
Физический способ реализации этих правил уточняется в tech gate: не обещаем готовые joints, prediction или детерминированную физику.

## 5. Сдача и квота

- Зона фургона — приёмник, не симуляция укладки в кузов. Она достаточно велика для дивана и подхода обоих игроков.
- Полная сдача: все восемь углов назначенного игрового bounding box предмета внутри объёма зоны; груз отпущен и остаётся так 0,5 секунды по времени authority.
- Выход части груза за границу либо новый захват сбрасывает этот интервал; несколько colliders не создают несколько зачётов.
- После подтверждения груз становится Delivered, исчезает из мира и больше недоступен. Выгрузки, возврата денег и повторной продажи нет.
- Хост одним переходом фиксирует Delivered, освобождение связей, ledger и сумму. Ключ зачёта — пара ShiftId + CargoId, повтор события/команды не добавляет стоимость.
- Клиент показывает подтверждённую хостом сумму; триггеры и UI сами деньги не начисляют. Можно превысить квоту, например 360/320.

## 6. Смена, спорные границы и интерфейс

- Оба игрока подключаются в подготовке; только хост запускает смену после готовности клиента. Поздний вход в Active исключён; подключение разрешено снова после возврата в подготовку.
- Таймер начинается при подтверждённом переходе хоста в Active, а не при загрузке сцены одним клиентом. Клиент подтверждает готовность после получения полного начального снимка.
- При нуле таймера хост завершает смену: сумма ≥ 320 — успех, иначе провал. Местонахождение игроков и несданный груз на этот исход не влияют.
- Ручная эвакуация F разрешена хосту, когда оба подключённых игрока находятся в зоне фургона и ничего не держат. После disconnect достаточно единственного оставшегося хоста; UI сообщает изменившийся состав.
- Эвакуация завершает смену немедленно с тем же правилом успеха/провала; при недоборе UI заранее пишет «Уехать: квота не выполнена». Подтверждённые позже сдачи не учитываются.
- На authority-шаге сначала проверяется deadline: если он уже достигнут, новые действия и сдачи не принимаются. Для шага до deadline дискретные команды идут по очереди; принятие эвакуации закрывает смену до последующих проверок зон.
- Итого груз, не ставший Delivered на предыдущем завершённом шаге к границе таймера/эвакуации, в итог не попадает. Клиентское время нажатия не даёт приоритета.
- После результата управление и зачёт заблокированы. Только хост может перезапустить: новая попытка с новым ShiftId, исходными спавнами, грузом, нулевой суммой и полным временем; соединения сохраняются, старые callbacks/команды отвергаются.
- Если клиент отключён, restart возвращает в подготовку и ожидает второго игрока; текущая сольная смена не выдаётся за полную проверку коопа.
- HUD: сумма/квота, оставшееся время, два участника и статус соединения, цель E, ручки/носильщики дивана и управляющий вращением, причины отказа.
- Подготовка: Host / Join по адресу и Start для хоста. Результат: успех/провал, сумма/цель, причина окончания, Restart только у хоста и выход в подготовку.

## 7. Технические границы

Применить предложенные границы [архитектуры](../docs/architecture/overview.md): Domain (правила/ledger), Application (команды/сессия), Unity adapters (ввод/мир/UI), Networking, явный Bootstrap.
ООП, инкапсуляция, композиция; обычные runtime-данные отдельно от MonoBehaviour и ScriptableObject-конфигурации. Без универсального DI, event-framework и глобального service locator.
Хост — единственный authority правил, игроков и грузовой симуляции; клиенты отправляют намерения, а не итоговые координаты/деньги. Сглаживание не меняет подтверждённый результат.
SessionId/ShiftId/CargoId/HandleId стабильны в своей области; CargoId не Unity InstanceID. Отправителя связывает хост с соединением. OperationId защищает повтор дискретных команд, ledger отдельно защищает зачёт.
Старый ShiftId, повтор с изменённым телом и команды отключённого соединения отклоняются. На restart очищаются состояние, связи, подписки и окно операций смены.

## 9. Работа с Unity и приёмка

По [CLI workflow](../docs/unity-cli-workflow.md) использовать существующий Unity CLI + Pipeline с явным project-path вложенного Unity-проекта.
Сначала версия CLI, обнаружение Editor и его статус; нужные команды и параметры искать в доступном CLI, а не предполагать API. Проверять конечный результат и фактическое состояние вместе с exit code.
В будущих разрешённых задачах dev владеет изменяющими Editor-командами; QA получает стабильные файлы/сцену и отдельное владение Editor для предусмотренных Play Mode/тестов/сборок. Одновременно их не запускать.
Сцену/объекты создавать поддерживаемыми командами, когда они доступны; после сохранения проверять файлы/.meta и Git diff. Недоступный Editor — непроведённая проверка, не PASS.
Итоговая приёмка требует два работающих процесса: коробка одним, диван только вдвоём, нормализованное движение, проходимые повороты, одинаковые квота/таймер/результат, отсутствие двойного зачёта и состояния старой смены.
При подготовке SPEC-001 проверялся только документ. С 31.10.2026 разрешены необходимые C#, сцены, префабы, asmdef, пакеты, настройки и проверки в scope IT1-01…IT1-06; реальные игровые проверки и Windows-сборка обязательны, статическое ревью их не заменяет.

## 10. Исключения и решение пользователя

Вне итерации: хоррор, враги, проклятия, повреждения, прокачка, магазин, сохранения, процедурная генерация, несколько домов, транспортное вождение, финальный арт/звук и поддержка контроллера.
Изменение согласованных игровых чисел и правил фиксируется отдельно, а не подменяет критерии ради прохождения проверки. Сетевая библиотека ещё не выбрана: обычный выбор версии и authority-переноски команда делает автономно в IT1-01, записывает в ADR до сетевой реализации и продолжает итерацию без повторного запроса разрешения.
