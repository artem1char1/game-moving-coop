# IT1-01 — инженерное решение первой итерации

Статус: решение разработчика в согласованном scope, передано QA. Пользователь разрешил реализацию SPEC-001. Этот gate фиксирует выбор до установки пакетов и сетевого кода; подтверждение работоспособности пакетов и механик относится к IT1-02…06. История ARCH-001 не переписывается.

## Сеть и совместимость

Выбран **Netcode for GameObjects 2.13.3 + Unity Transport 2.6.0**, client/server topology, один host и один client. Это готовые Unity-пакеты, не собственный UDP/TCP-транспорт. Unity Editor остаётся 6000.6.7f1, URP — существующая версия. Установку выполнить отдельным следующим изменением, закрепить версии в manifest/lock.

31 октября 2026 получены официальные registry-метаданные:

| Пакет | Поле `unity` | Объявленные зависимости / вывод |
| --- | --- | --- |
| NGO 2.13.3 | 6000.0 | transport 2.6.0, mono-cecil 1.11.4; выбираем эту patch-версию ветки 2.x |
| Transport 2.6.0 | 2022.3 | burst 1.8.24, collections 2.2.1, mathematics 1.3.2; фиксируем версию, которую объявляет NGO |
| NGO 3.1.0 | 6000.7 | Требует более нового Unity, не выбираем |

Источники: [NGO registry](https://packages.unity.com/com.unity.netcode.gameobjects), [Transport registry](https://packages.unity.com/com.unity.transport). Запросы: PowerShell `Invoke-RestMethod -Uri <registry-url>`, чтение `versions.'2.13.3'`, `versions.'2.6.0'`, `versions.'3.1.0'` и полей `unity`/`dependencies`; exit 0. По минимуму версии выбранные пакеты допускают текущий Editor. Это **метаданные совместимости, не фактически пройденная компиляция**. В проекте уже есть более новые транзитивные Collections/Burst; UPM должен разрешить совместный граф, а затем нужна проверка компиляции. Не понижать молча существующие пакеты ради решения конфликта; при конфликте уточнить этот ADR в разрешённом scope.

Варианты: NGO 3.x отклонён из-за minimum Unity; NGO 2.7.0 также доступен, но не выбран вместо более нового patch-ряда 2.13.3; отдельный сторонний стек не нужен для ограниченного LAN-среза. Steamworks, Relay, Lobby, NAT traversal, dedicated server, distributed authority и host migration не добавляются.

Сетевой адаптер использует NGO NetworkManager/UnityTransport и одну server-owned session bridge. Намерения передаются RPC; [официальная документация RPC 2.13](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/advanced-topics/message-system/rpc.html) описывает server-targeted вызовы. Отправитель берётся из receive metadata; клиентский PlayerId не доверяется. Состояние смены и позы реплицируются server→client снимками; host-представление читает тот же подтверждённый state. Самостоятельной клиентской симуляции/prediction и конкурирующего NetworkTransform writer нет.

Подключение: UDP порт 7777, host listen на 0.0.0.0, client default 127.0.0.1; LAN — ввод адреса хоста. Максимум два игрока вместе с хостом; подключение только в Preparing. Начальный полный снимок с SessionId/ShiftId, список игроков и правила должны быть применены до Ready. Обрыв хоста ведёт в preparation с причиной. Возврат после результата и состав участников сверяются с ТЗ; прежнее соединение не восстанавливается как reconnect в Active.

## Authority и доставка команд

- Только host обновляет игроков, груз, ручки, таймер, фазу и ledger. Domain/Application не зависят от NGO/Unity API; transport оборачивает сценарии.
- Фиксированный authority шаг 0.02 с; network input и snapshots — 20 Hz для первого среза. Снимок содержит epoch/ShiftId и revision; старые снимки отбрасываются, разрыв базы требует полного снимка. Небольшая сцена позволяет полные снимки без преждевременной delta-системы.
- Дискретные E/F/Start/Restart — надёжные команды с OperationId и результатом. На authority обработка последовательно; host локально тоже ставит команду в очередь, не обходит валидацию. Порядок deadline/эвакуации/сдачи соответствует SPEC §6.
- Continuous WASD/Q/R — полный текущий ввод с возрастным sequence, без накопления пакетов-команд; host принимает только возрастающий sequence этого соединения и текущей смены. Векторы валидируются (конечные числа, длина не больше 1), скорость/угловая скорость задаются хостом.
- Отправлять continuous input каждые 50 мс, включая нулевой. **500 мс** без нового валидного ввода по monotonic host time → обнулить движение/вращение и применить обычное правило отпускания: освободить коробку либо обе ручки дивана, включая approach reservations. Старый/повторный пакет не освежает таймер.
- Потеря фокуса немедленно обнуляет локальный ввод, посылает zero input и **надёжную дискретную release/focus-команду** с ShiftId/OperationId. Authority обнуляет ввод и тем же правилом освобождает коробку либо обе ручки дивана, включая approach reservations; повтор команды/timeout безопасен, старый ShiftId отвергается. Нулевые heartbeat в фоне не заменяют эту команду и не удерживают участие. При полном прекращении доставки release/focus и input страховкой служит stale timeout; надёжная команда при сохранённом соединении повторно доставляется транспортом. После focus loss игровые дискретные действия прекращаются до возврата фокуса; груз автоматически заново не захватывается. Для двух локальных процессов включается run-in-background, но фокус не даёт чужому процессу клавиатурный ввод.
- При disconnect сразу удалить ввод и связи, не ждать stale timeout. При restart очистить вход/sequence/окно операций и изменить ShiftId. Старые команды не становятся командами новой смены.

## Контролируемая переноска и коллизии

Выбор для первого среза: **плоская 2.5D кинематическая симуляция с collision queries на host**, без joints, свободного падения, импульсов и передачи сетевого владения грузом. Груз — box footprint/volume, игрок — capsule, пол один уровень. Это отвечает неподвижному отпущенному грузу из SPEC. Не разрабатываем лестницы/рампы/разрушаемые препятствия.

Обычный игрок движется capsule sweep с ограниченным slide вдоль стены; игроки не блокируют друг друга. Стены и свободный груз — препятствия. Носильщик не толкает свой удерживаемый груз: этот контакт исключается явно, но остальные препятствия сохраняются. Layer masks и идентичности фильтруются, а не отключаются все коллизии игрока.

Для сборки «груз + носильщики» сначала вычисляются общие translation/rotation из правил SPEC. За шаг выполняются малые подшаги: линейный не более 0.04 м, угловой не более 1°. Для каждого проверяется весь путь **каждого** collider сборки: sweep трансляции, конечное overlap и консервативная оболочка углового движения с учётом радиуса до наиболее удалённой точки. Один overlap только в конечной позе недостаточен: угол может пересечь стену между позами. Носильщики проверяются и по дуге их перемещения вокруг pivot; пол отделён от горизонтальных препятствий. Защита учитывает другие коробки и интерьер, а не только стены.

При блокировке допускается отдельно проверить безопасную translation без поворота либо поворот без translation; всё запрещённое остаётся в последней безопасной позе. Одна принятая подпоза применяется ко всей сборке атомарно. Никакого «протолкнуть груз»/snap через коллизию, скрытой клиентской телепортации или локального исправления ledger. Для первого среза skin 0.01 м; габариты маршрута проверяются с этим запасом. Консервативные проверки могут блокировать допустимое тесное движение — это известный риск playtest, а не повод уменьшить безопасность до непроверенного endpoint overlap.

Unity предоставляет [BoxCast](https://docs.unity3d.com/6000.6/Documentation/ScriptReference/Physics.BoxCast.html) и [OverlapBox](https://docs.unity.com/en-us/engine/6000.6/script-reference/unityengine/physics/overlapbox); сочетание запросов и безопасные подшаги — наше решение, а не обещание встроенного решения совместной переноски. Конкретные world queries можно заменить после наблюдений, сохранив единый authority и инварианты.

### Подход к ручке без snap

E резервирует выбранную свободную ручку только после проверки диапазона 1.2 м, LOS и свободного допустимого места рядом с ней. Рабочая цель — точка носильщика вне collider груза с отступом радиуса capsule + skin; она не равна центру геометрической ручки.

Игрок плавно сближается к цели на host с обычным capsule sweep, максимум 4 м/с, не перескакивает остаточную дистанцию. В это время ввод движения/вращения не переносит груз. Достижение в пределах 0.05 м завершает attachment. Если путь заблокирован, 1 с без достижения цели, повторное E или disconnect — отменить резервирование с причиной и освободить ручку. Во время подхода груз неподвижен, так что цель не убегает. Первый attached носильщик дивана ждёт второго; начать движение можно только после завершения обоих подходов. Резервация считается занятым ресурсом при гонке, но не готовым носильщиком. Если первый отпустил/отключился, отменяются оба attachment/approach.

Базовые размеры игрока для проверки маршрута: capsule radius 0.25 м, height 1.5 м. Диван 2.2×0.9 м, ручки у коротких торцов, носильщики снаружи торцов. Ширина проёмов не меньше 1.6 м и достаточно широкие комнаты поворота; фактическую проходимость проверять всей сборкой, включая подходы, а не из одного размера двери.

## Проверки gate и следующие доказательства

На этом шаге выполнено только чтение registry, локальных документов и Unity status: CLI 1.0.0-beta.15, точный project-path, result ready/compiling=false/domainReload=false/playMode=stopped, Unity 6000.6.7f1. Нет установки пакетов, изменения сцены, Play Mode или игровых тестов. Изменены только этот ADR и дополнение decisions.md.

После QA gate продолжить разрешённые IT1-02…06 без повторного запроса обычных инженерных решений. До объявления сетевого spike успешным нужны разрешение пакетов и реальная компиляция; два процесса должны подтвердить подключение/начальный snapshot, host authority и отказ третьему/позднему клиенту. До приёмки переноски — два носильщика, sweep угла/тела/ручек, stale input, disconnect в подходе/переноске и повторные команды. До итоговой приёмки — оба маршрута квоты, таймер/эвакуация, два restart и неизменность ledger.

Для воспроизводимой проверки заложить небольшой development-only сценарий запуска двух Windows-процессов с аргументами host/join/scenario и структурированным логом. Автоввод заменяет только источник намерения и проходит обычные transport → Application → authority → collision queries; не выставляет позы/деньги напрямую. Задача не требует отдельного production-framework. Эти сценарии дополняют проверку UI/удобства, а не заменяют её. QA получает конкретные процессы/логи и стабильное состояние Editor.
