# Экономный рабочий цикл

Политика agent-policy.json — ориентиры маршрутизации, не технический лимитер API. Пауза игры сохраняется.

1. Классифицировать S/M/L/C, выбрать минимальных исполнителей. C включает сеть, квоту/ledger, рестарт, сохранения, безопасность. План C может составить координатор; независимый QA обязателен. Всю тройку запускать только с записанным обоснованием.
2. Начинать с rg/дерева/символов и diff, не полного сканирования. Первоначально 3–8 нужных файлов; расширение оправдать зависимостью. Для маленькой правки достаточно одного. Уже известный неизменённый текст повторно не читать; краткие сводки привязывать к commit и hash/mtime, инвалидировать после изменения контракта.
3. Новым агентам передавать fork_turns=none и пакет ниже, а не историю. Не будить старых агентов ради ready/status. Существующую длинную историю нельзя очистить задним числом: новую самостоятельную задачу лучше передать свежему агенту с тем же назначением роли. Модель/effort наследуются; изменения профиля — отдельное явное решение. Нет обещаний экономии кэша или подписочного лимита.
4. На вызов назначить конечный результат и не более двух раундов содержательного исправления. Один технический повтор; одинаковый запрос без нового evidence не повторять. При превышении ориентира координатор записывает причину и новый предел, без автоматического опроса пользователя для обычной разрешённой работы. Обязательные тесты не отменять; не заявлять done при неполной проверке. Не устанавливать фиктивные token-budget ключи в Codex config.
5. Ожидание — один wait до45с, не цикл коротких опросов. Зависимые действия последовательно; независимые чтения объединять. Пользователю — новые результаты/блокеры, без повторов прежнего статуса; требования интерфейса к обновлениям соблюдать.
6. Один компактный итог вместо отдельного отчёта на каждую передачу. Большие логи — work/, вывод tools ограничивать нужным фрагментом; повторные прогонки только при изменениях, сбое или неразрешённом риске. Для S/M не требовать PM-церемонию и отдельный документ QA. Полезные прежние документы/тесты не удалять.

Пакет задания (в сообщении, отдельный файл не обязателен):
```
task_id / class / summary
files: path + зачем; symbols; dependencies; diff/base commit
acceptance; constraints; allowed writes / Editor owner
budget: max calls, revision rounds, checkpoint time; rationale
result: ожидаемый артефакт/проверки
```

Handoff (обычно до200 слов; расширить при сложном дефекте):
```
TASK_ID; STATUS: done|partial|blocked
CHANGED_FILES; SUMMARY: 1–5 предложений
TESTS: команды + фактический результат; evidence path
RISKS; NEXT_ACTION
```

Журнал: work/production/usage.jsonl, одна строка на завершённое задание/значимый checkpoint, не на каждое чтение. Поля: task_id, class, date, agents/model/reason, calls, tokens_in/out/cached, cost_or_limit, files_read, repeated_reads, elapsed, result, tests, defects, escalations. Неизвестное = null с причиной; ноль только если измерен. Учитывать главного агента и модельные инструменты, когда метрики доступны. Не хранить секреты/полные транскрипты.

Пилот: следующие15–30 сопоставимых задач без искусственного запуска ради статистики. Сравнивать S/M/L/C отдельно, завершённые задачи и дефекты. При наличии точных данных считать median/p90 входных+выходных токенов и повторных чтений; при отсутствии честно показывать null. Цели30%/50% не считать достигнутыми по сокращению символов инструкций. Недельную сводку строить по запросу/при накоплении данных, фоновая автоматизация не создавалась.
