# Команда проекта

Это кооперативная игра для Steam: изометрия, простая мультяшная графика, переноска мебели из домов и денежная квота. Концепты в `outputs/` — визуальные ориентиры, не готовые игровые ассеты. Пользователь выбрал Unity; существующий проект использует Unity 6000.6.7f1, URP и C#. Сетевой стек и точные правила ещё не выбраны. Не превращать предложения из переписки в утверждённые требования.

## Оркестрация

Пользователь поручил вести разработку через трёх субагентов. Основной агент — координатор и единственная точка общения с пользователем. Роли определены в `.codex/agents/`.

1. `project_manager` уточняет существующие требования, ведёт `work/production/backlog.md`, разбивает разрешённую работу на небольшие последовательные задачи с критериями приёмки.
2. Координатор передаёт готовую задачу `gamedev_developer`: ID, цель, границы изменений, зависимости, критерии и проверки. Разработчик реализует её и возвращает список изменений, результаты проверок и ограничения.
3. Координатор передаёт реализацию `qa_reviewer` для независимого код-ревью и доступных проверок. Если есть дефекты, возвращает замечания разработчику; после исправлений QA перепроверяет затронутое поведение.
4. `project_manager` закрывает задачу только после подтверждённых критериев и результата QA. Координатор сообщает пользователю результат и существенные ограничения.

Использовать доступные инструменты субагентов; не создавать отдельные пользовательские чаты. Если пользовательские роли ещё не загружены клиентом, явно передавать содержимое соответствующего TOML как инструкции при запуске обычного субагента. Не заявлять, что конфигурация автоматически загрузилась, без подтверждения.

Повторно использовать существующих агентов. Не запускать вложенных субагентов: координатор плюс три роли укладываются в четыре доступных слота. Зависимые этапы выполнять последовательно; параллельно разрешены только независимые задачи. Каждый субагент получает конкретное поручение, а не бесконечную работу в фоне.

## Владение и качество

- PM изменяет только производственные документы. Разработчик — назначенный код и связанные материалы. QA — только назначенные отчёты; не исправляет проверяемый код самостоятельно.
- Не редактировать одни файлы одновременно. QA получает стабильный снимок: разработчик приостанавливает изменения на время проверки. При отсутствии Git передавать точный перечень файлов и проверяемое состояние.
- Статусы: `backlog -> ready -> in_progress -> review -> done`; замечания возвращают задачу в `in_progress`. `blocked` означает конкретную внешнюю зависимость; `cancelled` сохраняет причину отмены. Записывать владельца, зависимости и доказательства проверок.
- Не отмечать невыполненные тесты как пройденные. Если нет движка, сборки или возможности проверить мультиплеер, явно записать это; статическое ревью не заменяет запуск игры.
- Проверять значимые риски: управление, камера и перекрытия стенами; столкновения и совместная переноска; повреждение и стоимость груза; однократное начисление квоты; повторный запуск смены; сетевое владение и отключение игрока, когда сеть появится.
- Не расширять задачу автоматически до всей игры. Не выбирать окончательно движок и не устанавливать крупные инструменты без задания, которое этого требует. Предлагать обоснованный выбор, если он необходим для следующего этапа.
- Для простых вопросов и мелких правок не проводить полный цикл команды. Для разработки функций, исправлений и этапного планирования применять описанный процесс.

Промежуточные материалы хранить в `work/`, пользовательские результаты — в `outputs/`. Общаться с пользователем по-русски.
